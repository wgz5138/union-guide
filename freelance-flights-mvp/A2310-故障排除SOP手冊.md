# A2310 故障排除 SOP 手冊

> 對應交付物 C：IP 被封鎖、網站結構微調、驗證碼卡關等常見爬蟲故障之標準應變與修復手冊。
> 內容基於本案開發過程中實際遭遇並排除之真實故障案例。

---

## 故障 1：間歇性「系統發生錯誤」（最常見）

**現象**：頁面顯示「糟糕！系統發生錯誤。」＋「重新載入」按鈕，非固定發生，同一網址有時成功、有時失敗。

**判斷**：此為 Google 端隨機性阻擋，非程式錯誤、非網路問題。

**系統現有應變**：
- 自動偵測此錯誤字樣，重新前往該網址，最多重試 8 次（`load_with_retry()`）。
- 詳情頁另有獨立的重試機制（最多 5 輪）。

**若重試 8 次仍失敗，人工排查步驟**：
1. 檢查 `logs/gflights.log`，確認是否「每一次」都失敗（連續失敗 vs 偶發）。
2. 手動開啟同一網址於一般瀏覽器，確認 Google Flights 服務本身是否正常（排除 Google 全站異常的可能）。
3. 若人工開啟正常、程式仍持續失敗：可能是該 IP 短時間內請求次數過多被暫時降權，
   建議降低執行頻率（拉長排程間隔）或間隔數小時後再試。
4. 若持續多日失敗：考慮啟用代理 IP（見故障 2）。

---

## 故障 2：IP 被封鎖 / 長期異常降權

**現象**：同一 IP 幾乎每次都失敗，即使拉長間隔仍無改善；換一個網路環境（如手機熱點）測試卻正常。

**判斷步驟**：
1. 用手機網路（非同一 IP）手動測試同網址是否正常。
2. 若手機正常、原本網路異常 → 可初步判定該 IP 已被列入降權名單。

**應變方案（依成本由低到高）**：
1. **降低頻率**：拉長排程間隔（如從每小時改為每 4–6 小時一次），觀察是否恢復。
2. **更換網路環境**：若為固定 IP（機房/雲端主機），申請更換對外 IP。
3. **導入代理 IP 服務**：長期高頻運行建議採用住宅型（residential）代理 IP 輪替，
   降低單一 IP 請求量。此為額外成本項目，需與委託方另行確認是否納入範疇。

## 故障 3：網站結構微調（改版）

**現象**：程式執行正常（無報錯），但抓到的資料數量異常（如突然變 0 筆），
或欄位內容明顯錯誤（如票價欄位出現非數字內容）。

**判斷**：Google 調整了頁面文字用語或排版，導致原本的比對邏輯失效。

**排查步驟**：
1. 將 `HEADLESS` 設定改為 `False`（若原本已是 False，跳過此步），親眼觀察頁面實際內容。
2. 在程式中加入除錯輸出，印出當下擷取到的原始文字（`li.inner_text()`），
   比對是否仍包含「小時」「直達／直飛」「轉機 N 次」等關鍵字樣，或用語已改變（例如
   Google 曾出現「轉機」「次轉機」兩種語序並存的情況，程式已同時涵蓋兩種）。
3. 依實際文字調整 `parse()` / `has_results()` 中的正則表達式或關鍵字清單。
4. 修正後，針對過去已知可正常運作的航線重新測試，確認資料正確再上線。

**設計原則**：系統採「內容特徵比對」而非固定 class 定位（見技術架構文件第二節），
故一般文字措辭微調通常只需調整關鍵字/正則，不需重寫整體邏輯。

## 故障 4：驗證碼 / 人機驗證卡關

**現象**：頁面出現 reCAPTCHA 或「請證明您不是機器人」等驗證畫面，非「系統發生錯誤」。

**判斷**：與故障 1 不同，此為更明確的機器人偵測攔截，通常代表該來源（IP／瀏覽器特徵）
已被較高等級的風控標記。

**應變方案**：
1. **不建議自動化嘗試破解驗證碼**（涉及違反目標網站服務條款風險，且技術上不穩定）。
2. 先確認是否為單次偶發：暫停排程數小時至一天後再試。
3. 若持續出現：視同故障 2（IP 被封鎖）處理，降低頻率或更換 IP／導入代理服務。
4. 若委託方需求為「絕不可卡驗證碼」的高保證等級，建議另行討論導入付費反爬蟲服務
   （如商用驗證碼解決方案）或改用官方/授權資料來源，此為原範疇外之額外投入。

## 故障 5：單一航班處理異常導致的例外（已修復案例）

**歷史案例**：抓取行李額度時，詳情頁在重新載入過程中遭遇 `Page.reload: net::ERR_ABORTED`
（瀏覽器導航被中斷），若未妥善處理會導致整支程式中斷、後續所有航線都無法繼續。

**根本原因**：詳情頁本身也會出現故障 1 的間歇性錯誤，原始重試邏輯在特定時機點呼叫
`reload()` 時，頁面已處於不穩定狀態（frame detached），導致例外未被攔截而向上拋出。

**已完成修復**：
- 所有詳情頁操作皆加入例外攔截，任何步驟失敗僅記錄警告、略過該筆行李資料，
  不影響其他航班與航線之抓取。
- 此為「單點故障隔離」設計原則的具體實踐：加值功能（行李額度）的失敗，
  絕不可拖累核心功能（票價/轉機/時間/航空）的完整性。

**維護提醒**：日後新增任何「點擊詳情頁」類的擴充功能（如未來新增航班號擷取），
應比照此原則，將該功能的例外處理獨立包裹，避免重蹈相同問題。

## 故障 6：Windows 中文環境下 .bat 排程腳本亂碼／指令跑掉（已修復案例）

**現象**：本機排程用的 `.bat` 檔案（如「設定每天自動抓取」腳本）執行時，
中文訊息顯示為亂碼（`'�' 不是內部或外部命令`），且 `@echo off` 未生效
（每一行指令都被逐行印出，而非只顯示執行結果）。**注意**：此為「顯示訊息出錯」，
`schtasks` 建立排程本身通常已成功執行，實際排程功能不受影響，僅提示畫面有問題。

**排查歷程**（記錄嘗試順序，供快速判斷卡在哪一關）：
1. **第一猜測**：中文全形括號「（）」出現在多行 `if (...) else (...)` 區塊內，
   cmd.exe 對此組合有已知解析缺陷 → 改用 `goto`/標籤結構完全避開多行括號區塊。
   （此為必要修正，但**非本案根本原因**，單獨此步驟並未解決問題。）
2. **第二猜測**：`.bat` 檔案缺少 UTF-8 BOM（位元組順序記號），導致 cmd.exe
   讀取檔案時誤用系統預設編碼解析中文字元 → 加上 UTF-8 BOM。
   （**仍未解決**；重新測試後出現一模一樣的亂碼與 `@echo off` 失效現象。）
3. **關鍵診斷**：發現故障現象在兩次修正後「一字不差」重複出現，判斷可能是
   測試方尚未取得最新版本（`git log -1` 核對後證實確有此情況，先排除此因素
   重新測試一次，確認問題依然存在，排除「測到舊版本」的可能）。
4. **真正根因**：目標機器為**繁體中文 Windows，系統原生編碼為 Big5**。
   即使檔案存為 UTF-8 並加上 BOM，該台機器的 cmd.exe **在解析 `.bat` 檔案本身
   內容時，並未依 BOM 辨識為 UTF-8，仍以系統預設 Big5 編碼讀取位元組**——
   `chcp 65001` 只影響「主控台輸出顯示」的編碼，不保證影響「批次檔案本身
   如何被讀取解析」，兩者是分開的行為，且在舊版 cmd.exe 上 UTF-8 BOM 偵測
   並不可靠。UTF-8 的多位元組中文字被拆散讀成不連續的 Big5 字元，desync
   到含有全形冒號「：」「；」的行附近開始整段解析錯亂。

**已完成修復**：
- 放棄「讓檔案宣告為 UTF-8」的思路，改為**讓檔案編碼直接對齊目標機器的系統
  原生編碼**：全部 `.bat` 檔案存成 Big5（Python `cp950`），`chcp 65001` 改為
  `chcp 950`，使宣告的 codepage 與實際檔案位元組編碼一致。
- 修復前務必確認：欲使用的文字內容**是否都能被 Big5 完整表示**（例如 emoji、
  罕見符號可能無法編碼），可用程式先行驗證（`text.encode('cp950')` 是否拋出
  `UnicodeEncodeError`）再轉檔，避免產生無法還原的內容。

**判斷準則（下次遇到類似案例）**：
- 若客戶的目標部署環境（伺服器/工作站）**語系明確是繁體中文 Windows**，
  本機批次腳本優先**直接採用 Big5 編碼**，不要預設用 UTF-8＋chcp 65001
  的組合，可省去這整輪排查。
- 若不確定目標機器語系或為跨語系团队共用，UTF-8＋BOM＋`chcp 65001` 仍是
  較泛用的起點，但需說明「舊版 cmd.exe 或特定語系環境可能仍有相容性風險」，
  不宜對客戶保證 100% 相容。
- 診斷時務必先**排除「測試方未取得最新版本」這個最基本的可能性**（核對
  `git log -1` 或檔案修改時間），再繼續往下深挖技術原因，避免在已解決的
  問題上重複排查、誤判修復無效。
