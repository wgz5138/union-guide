## 一、系統流程總覽

```
排程觸發（本機工作排程器 / 手動執行）
        │
        ▼
啟動瀏覽器（持久化設定檔 + stealth 偽裝）──────┐
        │                                    │  反爬蟲應對機制
        ▼                                    │  （見第三節）
組出搜尋網址，前往 Google Flights ─── 失敗？──┘
        │                    │
        │ 成功                │ 重試（最多 8 次，指數退避概念）
        ▼                    │
偵測「結果是否已載出」 ──否──┘
        │ 是
        ▼
從列表擷取每一班（票價/轉機/時間/航空）──去重──┐
        │                                    │
        ▼                                    │
逐班點進詳情頁擷取「行李額度」 ── 詳情頁報錯？──┘
（詳情頁重試，任何錯誤只略過該班，不中斷整體）
        │
        ▼
結構化輸出（CSV + JSON） + 寫入執行日誌
```

## 二、爬蟲定位邏輯（如何在頁面中找到資料）

### 2.1 為什麼不用固定 CSS class
Google Flights 的元素 class 名稱為**動態產生的亂碼**（例：`pIav2d`），且會隨版本更新而改變。
若程式寫死某個 class，Google 一改版就會整支失效。

### 2.2 採用「內容特徵比對」取代 class 比對
- **航班卡片定位**：掃描頁面所有 `<li>` 元素，篩選出「同時含有 `$價格` 與『小時』或『分鐘』文字」的項目，
  視為一張航班卡片（見 `extract()` 函式）。此邏輯不依賴任何 class 名稱，改版時較不易失效。
- **票價擷取**：以正則表達式 `\$\s*[\d,]{3,}` 抓取含 `$` 的數字（`parse()` 函式），
  避免誤抓「碳排放量：200 公斤」等其他數字。
- **轉機次數**：比對「直達／直飛／Nonstop」判定為 0；否則比對「轉機 N 次」或「N 次轉機」
  （Google 介面有兩種語序，皆已涵蓋）。
- **時間**：中文時段前綴（清晨/上午/中午/下午/晚上/凌晨）+ `H:MM` 格式。
- **航空公司**：以已知航空公司中文名稱清單比對（清單可隨新增航線持續擴充）。
- **行李額度**：需點進航班詳情頁，比對包含「手提行李」或「託運行李」字樣的文字行（`parse_baggage()`）。

### 2.3 定位航班卡片並點擊詳情（`click_flight()`）
以「票價（含 `$` 前綴，避免 `$5,699` 誤配 `$15,699`）＋ 出發時間」組合比對，
在列表中找出對應的那張卡片並點擊，避免同頁多航班時點錯。

## 三、反爬蟲應對機制

Google Flights 具備**間歇性的伺服器端阻擋**（畫面顯示「系統發生錯誤」），
並非固定規則式攔截，而是行為/流量特徵判斷後的隨機阻擋。應對方式如下：

| 機制 | 說明 |
|---|---|
| **Stealth（自動化特徵隱藏）** | 注入 JS 移除 `navigator.webdriver` 等瀏覽器自動化偵測旗標；停用 Chromium 的 `--enable-automation` 標誌與資訊列 |
| **持久化瀏覽器設定檔** | 使用 `launch_persistent_context` 保留 cookie 與同意設定，使每次執行「像同一位真實使用者持續使用瀏覽器」，而非每次都是全新、可疑的匿名連線 |
| **真實瀏覽器環境參數** | 設定正常的 User-Agent、`zh-TW` 語系、`Asia/Taipei` 時區、一般桌面解析度視窗尺寸，避免無頭/異常環境特徵 |
| **非 Headless 模式** | 經實測，`headless=True` 明顯提高被阻擋機率；正式環境採 `headless=False`（見第五節之部署限制） |
| **禮貌性等待與退避** | 每次載入後等待 11 秒讓內容渲染，失敗後再等待數秒才重試，避免高頻率請求觸發保護機制 |

## 四、錯誤回復流程（高穩定性設計）

### 4.1 分層重試策略

| 層級 | 重試次數 | 說明 |
|---|---|---|
| 列表載入（`load_with_retry`） | 最多 8 次 | 每次判定「是否已出現真實票價＋無錯誤字樣」，未達成則重新前往該網址 |
| 詳情頁載入（`fetch_baggage`） | 最多 5 輪，每輪輪詢 16 次 | 詳情頁同樣會間歇報錯，比照列表邏輯重試；逾時則放棄該班行李（不影響其他班） |

### 4.2 「結果已載出」的判定邏輯（避免誤判）
早期版本僅以「畫面含『小時』」判斷是否載出成功，但 Google 頁尾固定文字
（「搜尋結果顯示的是 24 小時內的資訊」）會造成誤判——畫面仍在載入中卻被誤認為已完成。
現行版本改為**必須同時具備「真實票價 `$數字`」與「小時」字樣、且不含錯誤字樣**才視為成功
（`has_results()` 函式），從根本解決此誤判問題。

### 4.3 錯誤隔離設計（單點失敗不影響整體）
系統採**三層防呆**，任一層級出錯都不會波及其他部分：

1. **航班層級**：單一航班的行李擷取失敗（如 `frame detached`、頁面在重載過程中
   中斷導航）僅略過該班，記錄警告後繼續下一班。此設計於實測中曾發生 Playwright 的
   `Page.reload: net::ERR_ABORTED` 例外，修正後驗證可正常略過並完整跑完全部航線。
2. **航線層級**：`_run_all_routes()` 對每條航線的處理都包在例外攔截中，任何未預期
   錯誤（含 `extract()` 擷取階段的例外）只使該航線記為失敗，不影響其他航線繼續執行、
   也不影響已抓到的資料與統計正常存檔。
3. **執行層級**：即使瀏覽器本身初始化失敗（設定檔損毀、環境異常等）導致完全無法
   啟動，`main()` 仍會攔截此例外，把「這次完全失敗」連同原因寫入成功率統計，
   確保交付物 C 要求的「每日執行日誌」不會因嚴重錯誤而整筆消失。

⚠️ **「單點隔離」不等於「照單全收」**：三層防呆解決的是「單一航班/航線失敗
不該拖累其他航線」，但**若本次執行的全部航線都失敗**（例如金鑰未設定、API
或目標網站整個異常等系統性問題），代表這不是單點問題，而是這次執行本身
就是失敗的。此時系統仍會：
- 把已查到的資料（若有）與失敗原因正確寫入 log／統計檔；
- 但**程式最終仍以非零結束碼（拋出例外）收尾**，讓排程系統（Windows工作
  排程器 log、GitHub Actions 執行狀態）能被動偵測到「這次整批失敗」，
  而不是把「全部失敗」誤判成「一切正常」而默默略過。
  兩支主程式（`gflights_scraper.py`、`travelpayouts_flights.py`）皆採此設計。

### 4.3.1 成功率判定準則
呼應交付物 B「成功率（未遭封鎖且數據完整）」之定義，系統的「成功」判定同時要求
兩個條件皆成立：① 頁面確實載出且未遭阻擋（`has_results()` 判定）；② 實際擷取到
至少一筆航班資料。若頁面顯示正常但擷取結果為空（可能為版面比對邏輯需更新），
仍記為失敗並附上原因，避免虛報成功率。

### 4.4 已知限制與因應方向
- 目前重試策略為「同一連線持續重試」，未整合代理 IP 輪替；長時間高頻執行若被判定
  為異常來源，重試次數再多也可能持續失敗。此為連續 7–14 天高成功率驗收之主要風險，
  詳見「A2310-回覆確認信」中與委託方之討論。
- 若需大幅提升穩定度，下一步可考慮：住宅型代理 IP 輪替、請求頻率隨機化、
  多設定檔輪替使用。

## 五、部署限制說明

- 目前驗證環境為 `headless=False`（有畫面瀏覽器），於**有圖形介面的 Windows 主機**上穩定執行。
- 若需部署至無圖形介面（headless）之雲端伺服器，建議：
  1. 使用虛擬顯示器（如 Xvfb）模擬圖形環境後以「有頭模式」啟動瀏覽器；或
  2. 改用 `headless=True` 並額外投入時間強化 stealth（目前實測 headless 模式反爬阻擋率較高，尚未在此模式下完整驗證）。
- 此限制已於回覆確認信中向委託方說明，待確認伺服器環境後補充對應部署文件。
