## 3. 兩套系統現況

### A) API 版（已完成、實測、雲端在跑）
- `travelpayouts_flights.py`：多航線、**中文地名自動轉代碼**（地名對照表）、單程/來回、
  **降價偵測**（`price_state.json` 記上次價，只在變便宜才通知）、Telegram 推播、繁中 Skyscanner 連結。
- **月份彈性查詢（2026-07-19 加）**：route 不填 `"month"` 就自動查
  `next_months(FLEX_MONTHS_AHEAD=3)`（這個月起連續 3 個月，跨年正確）、合併結果。
  緣由：查證不到 Travelpayouts API `departure_at` 留空的官方行為（文件頁 403 打不開），
  不賭未知行為，改在自己這端把月份清單算好、行為 100% 可控可測。
  `ROUTES` 預設已改成不寫死月份（原本 "2026-09" 寫死會在該月過後永遠查不到卻無提示，
  已修正）。
- **預設查來回（2026-07-20 改，取代舊的「彈性月份只做單程」限制）**：
  使用者原本測「查 高雄 東京」不打月份，發現查到的是單程、還轉機，
  跟預期不符（她要「來回」且「盡量直航」）。查證發現：`round_trip` 舊版
  判斷式是 `"return" in route`——沒打第二個月份就一定是單程，這是
  2026-07-19 做彈性月份查詢時順手訂的（並非使用者要求），跟 `THRESHOLD`
  注解「多國來回」的原始設計意圖對不上。已改成 `round_trip = not
  route.get("one_way", False)`：**預設一律查來回**，沒給明確回程月份
  （`route["return"]`）就用「跟去程同一個月」回程（`_fetch_offers()` 裡
  `route.get("return") or month`）——這正是彈性月份查詢加上去之前，
  `ROUTES` 原本的寫法（`"month": X, "return": X`），只是現在自動補上、
  不用手寫，也因此原本「彈性只能單程」的限制自然解除，不需要另外設計
  去回月份配對邏輯。想改回單程：`route["one_way"] = True`；Telegram
  端打「單程」／`single`／`one way` 這幾個字（不分大小寫）會自動設定，
  見 `telegram_bot.py` 的 `單程關鍵字`。因為所有查詢路徑（一般查詢/
  探索模式/每日排程）都共用底層的 `_fetch_offers()`，這一處改動同時
  影響全部——不用三個地方各改一次，也不會漏改。
- `telegram_bot.py`：**雙向** bot，在 Telegram 打「查 高雄 東京 2026-09」即查（解析很寬鬆），
  **也可以不打月份**（例：「查 高雄 東京」），會自動用上面的彈性月份查詢；
  預設查來回，加「單程」兩字改查單程。
- **口語月份（2026-07-21 加，`resolve_month()`）**：使用者打「查 高雄 中國
  直飛 12月」結果查到的是 9 月——月份辨識原本只認 `\d{4}-\d{2}`（完整
  「2026-12」），「12月」完全沒被認出來，`months` 是空的，程式當成
  「沒打月份」退回彈性查未來 3 個月（現在是 7 月，剛好落在 7-9 月，
  9 月最便宜就跑出 9 月，不是 bug 是誤判成沒填）。已加
  `travelpayouts_flights.resolve_month(month_num)`：只給月份數字，
  自動算出「今天以後最近一次」出現的那個年份（月份 >= 現在月份算今年，
  比現在月份小就跨年算明年，不會抓到已經過去的月份）。
  `telegram_bot.py` 的 `handle()` 原本用一個組合正則
  `\d{4}-\d{2}|(?:1[0-2]|[1-9])月份?` 一次 `finditer` 掃過整句，
  照文字裡原本出現的先後順序組成 `months` 列表（事後健檢時發現分兩輪
  處理會把去回程順序弄反，已改成這個「同一次掃描」寫法——後續
  `parse_natural_dates()` 加了更多格式支援，仍然沿用這個同一次掃描
  的核心原則，見下一則「自然語言日期」）。
- **自然語言日期（2026-07-21 加，`parse_natural_dates()`／
  `NL_DATE_PATTERN`）**：使用者要「更聰明的自然語言日期解析」，
  在 `resolve_month()` 基礎上擴充成一個統一的正則＋解析函式，
  取代 `telegram_bot.py` 裡原本自己寫的月份正則。支援：
  - 完整年月：`2026-12`
  - 阿拉伯數字或**中文數字**月份：`12月`／`十二月`／`12月份`
  - 可選年份前綴（不加就沿用 `resolve_month()` 的「今天以後最近一次」
    邏輯）：`明年3月`／`今年十二月`／`後年5月`
  - 相對月份：`這個月`／`這月`／`本月`／`下個月`／`下月`／
    `下下個月`／`下下月`
  - 相對日期換算成落在哪個月（`month_from_date_offset()`）：
    `今天`／`明天`／`後天`／`大後天`／`下週`／`下星期`／
    `N天後`／`N週後`／`N個月後`
  只解析到「月」的粒度，**不解析到某一天**——因為 Travelpayouts
  API 本身就是用 `departure_at="YYYY-MM"` 查整個月份的最低價
  （見 `_fetch_offers` 說明），解析到日期反而是假精確、沒有意義。
  `NL_DATE_PATTERN` 是模組層級的公開正則常數，`telegram_bot.py`
  同時拿它來（a）用 `parse_natural_dates()` 解析月份、（b）用
  `.sub(" ", rest)` 清掉月份文字方便找地名——**find 跟 strip 保證用
  同一份正則**，結構上就杜絕「兩邊認定的月份文字範圍不一致」這整類
  問題（這正是上一則「口語月份」踩到的 bug 類型，這次直接從架構上
  避免，不是頭痛醫頭）。
  中文數字轉換：`一~十二` 對照表（`_中文數字`），沒對到的才退回
  `int()`（正常不會發生，正則已經限制只有這些字元）。
  已用假的「今天」測過月中/月底/跨年邊界（例如 11 月中打「5個月後」
  正確跨到明年 4 月、「下下個月」正確跨到明年 1 月），也測過跟完整
  `YYYY-MM`／中文數字混打在同一句時順序不會反。
- **優先直飛（2026-07-20 加，`_prefer_direct()`）**：使用者說「盡量能直航」——
  `search_offers()`（一般查詢）本來就有 `direct_first` 邏輯（有直飛就只列直飛），
  但抓「最便宜一張」的 `search_cheapest()`（探索模式跟每日排程都靠這支）
  沒有，會選到轉機比較便宜的那張，跟使用者期待不符。已抽出共用的
  `_prefer_direct(offers, direct_first=True)`：有直飛選項就只在直飛裡比價，
  **這條航線根本沒有直飛才退回全部（含轉機）**——不會因為堅持直飛而查不到票。
  `search_cheapest()`／`search_offers()` 現在都吃這個共用邏輯，`direct_first`
  預設都是 `True`。探索模式的回覆訊息之前完全沒顯示轉機資訊，使用者根本
  分不出來，已補上「直飛／轉N次」標示。
- **探索模式（2026-07-19 加，`explore_deals()`）**：想去別的國家但還沒決定去哪 →
  傳「探索」或「探索 高雄」（不用填目的地），會掃一輪 `ROUTES` 裡設定的那幾個國家
  （改 `ROUTES` 就等於同時改了探索範圍，不用維護第二份清單），
  優先秀「跟上次查到的價格比，降價幅度（%）大」的，沒有降價紀錄的才用
  「價格低到高」補在後面。降價幅度是跟 `price_state.json` 比較，跟每日排程
  **共用同一份記憶檔**——查得越勤，比較基準越準；同一天連續查兩次通常不會
  再顯示降價（第一次查完就把這次價格存成新的「上次」了），這跟其他地方
  「只在變便宜時才通知」的邏輯一致，不是 bug。
  觸發關鍵字見 `telegram_bot.py` 的 `探索關鍵字`（探索/驚喜/隨便看看/有什麼便宜/
  不知道去哪/隨機）；口語變化太大（例：「隨便看看有沒有便宜的」）偶爾會誤判成
  「看不懂的地名」而回覆友善提示，這是自然語言解析的已知限制，不是 bug——
  使用者只要照說明打「探索」或「探索＋地名」就一定會動。
  安全面：跟既有查詢一樣，逐國家 try/except（單一國家失敗不中斷整輪）、
  API 呼叫間仍有 1 秒禮貌延遲、不接受未知地名直接打 API（先擋在 handle() 內）。

- **每日總結（2026-07-20 加，`send_daily_summary()`）**：緣由是使用者回報
  「TG 完全不會推便宜機票」——查 GitHub Actions 實際 log
  （run 29673130764，2026-07-19 04:19 UTC）才發現**不是壞掉**：
  Travelpayouts 資料是快取，常常連續好幾天價格完全沒變（log 顯示
  「最低 7950 TWD（上次 7950），沒變便宜，不通知」），而 `notify()`
  的規則是「只在變便宜時才推」，於是變成安靜到像沒在跑一樣。
  解法：`main()` 迴圈現在不管有沒有觸發 `notify()`，每條航線都記一行
  （價格/查無票價/失敗），跑完不管今天有沒有值得通知的降價，
  **都會另外推一則「🕐 機票日報」總結**（時間戳用 `TW_TZ` 轉成台灣時間，
  因為 GitHub Actions 跑在 UTC；`datetime.now(timezone.utc).astimezone(TW_TZ)`

- **防止重複啟動（2026-07-20 加）**：加 log 後使用者實際回報就是 409 衝突，
  一路 4 次重試訊息連續出現。根因：`啟動聊天機器人.bat` 用**前景**
  `python.exe`（會留一個看得到的黑視窗），`開機背景啟動.bat`／
  `背景啟動機器人.bat` 用**背景** `pythonw.exe`——兩個是不同的進程名稱，
  而舊版 `停止機器人.bat` 只殺 `pythonw.exe`；如果使用者兩種都點過
  （例如照之前的說明打開視窗版測試，但開機時背景版早就自動跑了），
  停止腳本殺不掉前景那份，新開的又會跟它繼續搶 `getUpdates` 而 409。
  加了兩層防呆，兩層各自解決一種情境，不互相依賴：
  ① **`telegram_bot.py` 自己擋（主要防線，跟哪個 `.bat` 點的無關）**：
     啟動時用 `acquire_lock()` 寫一個帶 PID 的鎖檔
     （`telegram_bot.lock`，已加進 `.gitignore`），偵測到鎖檔裡的 PID
     還活著（Windows 用 `tasklist /fi "PID eq X"` 查，非 Windows 用
     `os.kill(pid, 0)`）就直接印錯誤、`return`、不進迴圈，不會製造
     409；鎖檔裡的 PID 已死（上次意外當機沒清乾淨）會自動判定成
     「沒人在跑」蓋過去，不會卡死自己。`release_lock()` 包在
     `finally` 裡，正常結束/Ctrl+C/例外都會清乾淨。
  ② **`停止機器人.bat` 改用 PowerShell `Get-CimInstance Win32_Process`
     比對命令列含 `telegram_bot.py`**，取代原本只認進程名稱
     `pythonw.exe` 的 `taskkill /im`——不管是前景 `python.exe`
     還是背景 `pythonw.exe` 都抓得到，也不會誤殺電腦上其他無關的
     python 程式（用命令列字串比對，不是無差別殺光所有叫 python 的
     進程）。
     ⚠️ 這支是 Windows PowerShell 腳本，雲端沙盒是 Linux、
     沒辦法實機跑過，只在本機用 Python 模擬過 `acquire_lock()`/
     `_pid_alive()` 的邏輯（同進程活著時擋住、進程死後自動解鎖），
     `.bat` 本身的 PowerShell 語法要使用者實機驗證才算數。

  不用再分別記兩件事。`git pull` 失敗（網路問題／本機衝突）會停下來印錯誤

## 7. .bat 中文亂碼案例（重要，別重踩）
- 使用者的 Windows 是**繁體中文 Big5 語系**。`.bat` 檔案若存成 UTF-8（不管加不加 BOM、
  用不用 `chcp 65001`），在該機器上會亂碼＋`@echo off`失效（cmd 讀檔案本身不理會
  BOM，仍用系統 Big5 解碼，desync 到全形冒號「：」「；」附近整段解析錯亂）。
- **正確解法**：`.bat` 檔案直接存成 **Big5(`cp950`)**，`chcp 65001` 改 `chcp 950`。
  已對全部 13 支 `.bat` 套用並實測通過（`設定Google機票每天自動跑.bat`／
  `取消Google機票排程.bat` 皆已在使用者機器驗證乾淨無亂碼）。
- 完整排查過程與判斷準則已寫入 `A2310-故障排除SOP手冊.md` 故障6，**未來若又遇到
  bat 亂碼，先看那一段，別重新從頭猜**。
- 教訓：診斷時曾因「使用者測試時剛好還沒 pull 到最新版」而誤以為修復無效，
